# Milestone 0: project layout and data schema

Status: approved 2026-11-07, with the decisions in section 10.

## 1. How the pieces fit

There are two programs and one folder of data between them.

1. **The book import tool** (Python, `tools/book_import/`). Runs on the DM's PC only. Reads the PDFs one book at a time, scores each page's text layer, runs Tesseract on poor pages, fixes known OCR slips, parses entries, validates them, and writes JSON into `data-pack/` plus an HTML review report into `reports/`.
2. **The character manager** (Electron + React + TypeScript, `app/`). Reads the data pack, merges in any user content (corrections and homebrew), and runs the character sheet, level-up wizard, editors and DM view. Saves characters as JSON files.
3. **The data pack** (`data-pack/`). Plain JSON, generated, git-ignored. The Windows build copies it into the app as a resource, so players get it without Python, Tesseract or the PDFs.

Rules logic (proficiency bonus, slots, AC, HP, rests, modifiers) lives in `app/src/shared/rules/` as small pure functions with no Electron or React imports. That keeps them easy to read and easy to unit test.

## 3. IDs and sources

Every entry has an ID made of kind, slug and book code, for example `spell.fireball.phb24`, `class.barbarian.phb24`, `subclass.ancestral-guardian.xge`. Book codes: `phb24`, `xge`, `tce`, `bgg`, and `user` for homebrew.

Every entry also carries a source block. The "legacy" tag on the sheet is simply `ruleset === "2014"`, so there is no separate flag to keep in sync.

```ts
type Ruleset = "2014" | "2024";

interface SourceRef {
  book: "phb24" | "xge" | "tce" | "bgg" | "user";
  ruleset: Ruleset;
  page: number | null;   // PDF page number as your PDF viewer shows it, not the printed number
  ocrUsed: boolean;      // true if any of the entry's text came from Tesseract
  flags: string[];       // import problems; empty means clean
}
```

## 4. Rules data schema (data pack and user content)

All rules files share the same base shape. A value the import could not read is `null` and has a flag explaining why. Nothing is filled in from memory.

```ts
interface EntryBase {
  id: string;
  kind: "class" | "subclass" | "species" | "background" | "feat" | "spell" | "item";
  name: string;
  source: SourceRef;
  summary: string;       // short rule summary for the sheet
  text?: string;         // full text, only where play needs it (spells, features with choices)
}
```

**Class.** The progression table must have exactly 20 rows. Class-specific columns (Rages, Rage Damage, Weapon Mastery, Cantrips, Prepared Spells and so on) go in `columns`, keyed by the column heading as printed, so no class needs special code to read its own table.

```ts
interface ClassEntry extends EntryBase {
  kind: "class";
  hitDie: number | null;
  primaryAbilities: Ability[];
  savingThrows: Ability[];
  skillChoices: { count: number; from: string[] } | null;
  weaponProficiencies: string[];
  armorTraining: string[];
  toolProficiencies: string[];
  startingEquipment: string;               // as printed
  subclassLevel: number | null;            // read from the book
  spellcasting: {
    ability: Ability;
    casterType: "full" | "half" | "third" | "pact";
    spellListId: string;                   // spells point back with their class list
  } | null;
  progression: ClassLevelRow[];            // 20 rows
  features: Feature[];
}

interface ClassLevelRow {
  level: number;
  proficiencyBonus: number | null;
  featureIds: string[];
  columns: Record<string, number | string | null>;
  spellSlots: (number | null)[] | null;    // index 0 = level 1 slots, up to 9
}
```

**Feature** (used by classes, subclasses, species, feats and homebrew).

```ts
interface Feature {
  id: string;
  name: string;
  level: number;                           // level gained in its own class or subclass
  summary: string;
  text?: string;
  source: SourceRef;
  activation?: "action" | "bonus" | "reaction" | "free" | "passive";
  uses?: {
    max: ValueRef;                         // e.g. { column: "Rages" }
    resetOn: "short" | "long" | "none";
    shortRestRegain?: ValueRef;            // some features regain part on a short rest
  };
  choices?: Choice[];
  modifiers?: Modifier[];                  // section 6
}

// A number, or a value looked up on the character.
type ValueRef =
  | number
  | { column: string }                     // from this class's progression row
  | { abilityMod: Ability; minimum?: number }
  | { proficiencyBonus: true }
  | { classLevel: true; multiplier?: number };

interface Choice {
  id: string;
  prompt: string;
  count: number;
  type: "skill" | "expertise" | "tool" | "language" | "feat" | "asiOrFeat"
      | "cantrip" | "spell" | "weaponMastery" | "option";
  from?: string[];                         // explicit list of IDs or option names
  filter?: { featCategory?: string; spellList?: string; maxSpellLevel?: number };
}
```

**Subclass**: `classId` (the class it belongs to, matched by name across rulesets so a 2014 subclass finds the 2024 class) and `features: Feature[]` at their printed levels.

**Species**: `size`, `speed`, `creatureType`, `traits: Feature[]` (with levels for traits that grow), `choices`.

**Background** (2024): `abilityOptions` (the three abilities it can raise), `originFeatId`, `skillProficiencies`, `toolProficiency`, `equipment`. 2014 backgrounds keep their own shape and are flagged as legacy.

**Feat**: `category` ("origin" | "general" | "fightingStyle" | "epicBoon" | "legacy"), `prerequisite` (printed text plus parsed `{ level?, ability?, other? }`), `repeatable`, `choices`, `modifiers`.

**Spell**: `level` (0 for cantrips), `school`, `castingTime`, `ritual`, `range`, `components` `{ v, s, m, material }`, `duration`, `concentration`, `classLists`, `summary`, `text`, `higherLevels`. The first seven fields are required; a missing one goes in the report.

**Item**: `category` ("weapon" | "armor" | "gear" | "tool" | "magic"), `cost`, `weight`, `attunement`, plus `weapon` `{ damage, damageType, properties, mastery, range }` or `armor` `{ armorType, baseAC, dexCap, strengthRequirement, stealthDisadvantage }`.

**User content** (content editor) uses exactly the same shapes. When the app loads, an entry in `user-content\` with the same ID as an imported entry replaces it and shows an "edited" tag; a new ID adds a new entry. The data pack itself is never written to by the app.

## 5. Character file schema

> **Updated in Milestone 1.** The exact format now lives in `app/src/shared/schema/character.ts`, which is the source of truth. It differs from the sketch below in these ways: use counters live on each feature (`customEffects[].uses.used`) instead of a separate `resourcesUsed` map; there is a `proficiencies` block (saves, skills, armor, weapons, tools, languages) that holds hand-entered values now and DM/manual additions later; and `attacks`, `spellcasting`, `spells`, `defenses`, `senses`, `speciesName` and `backgroundName` were added so a character can be fully entered by hand before the data pack exists.

One JSON file per character. The file stores what the player chose and what has happened in play. Things that can be worked out (proficiency bonus, save DC, AC, max slots) are calculated, not stored, so they can't drift out of sync. The one exception is Milestone 1 (see section 8).

```ts
interface CharacterFile {
  schemaVersion: 1;                        // lets later versions upgrade old files
  id: string;                              // random UUID
  name: string;
  player: string;
  portrait: string | null;                 // small embedded image, so it survives Google Drive

  speciesId: string | null;
  backgroundId: string | null;
  backgroundIncreases: Partial<Record<Ability, number>>;  // the +2/+1 or +1/+1/+1 choice
  abilityMethod: "standardArray" | "pointBuy" | "rolled" | "manual";
  baseAbilities: Record<Ability, number>;  // before background and ASIs

  levels: LevelRecord[];                   // one record per level taken, in order
  subclasses: Record<string, string>;      // classId -> subclassId

  proficiencyOverrides: Record<string, "none" | "proficient" | "expertise">;  // manual toggles
  weaponMasteries: string[];
  spells: { known: string[]; prepared: string[]; alwaysPrepared: string[] };

  inventory: InventoryItem[];
  coins: { cp: number; sp: number; ep: number; gp: number; pp: number };

  state: {
    hpCurrent: number;
    tempHp: number;
    tempHpExpires: Duration | null;
    hitDiceUsed: Record<string, number>;   // "d12" -> 1
    deathSaves: { successes: number; failures: number };
    inspiration: boolean;
    exhaustion: number;
    conditions: string[];
    spellSlotsUsed: number[];              // per slot level
    resourcesUsed: Record<string, number>; // feature ID -> uses spent
    toggles: Record<string, boolean>;      // e.g. "raging": true, drives conditional modifiers
  };

  customEffects: CustomEffect[];           // homebrew features, curses, conditions (section 6)
  manualValues: ManualValues;              // hand-entered numbers, used instead of calculated ones
  dmOverrides: {
    featureLevels: Record<string, number>; // feature ID -> level it is gained at on this character
    replacedEntries: Record<string, string>; // swap one entry for another on this character
    modifiers: Modifier[];                 // DM adjustments to any stat
  };
  notes: { general: string; backstory: string; allies: string; [tab: string]: string };
}

// Any field set here wins over the calculated value. In Milestone 1 everything
// is entered here by hand; from Milestone 3 most of it is calculated and these
// stay empty unless someone wants a manual override.
interface ManualValues {
  classes: { name: string; subclass: string; level: number; hitDie: number }[];
  maxHp: number | null;
  proficiencyBonus: number | null;
  armorClass: number | null;
  speed: number | null;
  initiativeBonus: number;                 // extra on top of Dex
}

interface LevelRecord {
  classId: string;
  classLevel: number;
  hp: { method: "max" | "average" | "rolled" | "manual"; value: number };
  choices: Record<string, string[]>;       // Choice.id -> what was picked
}

interface InventoryItem {
  itemId: string | null;                   // null for a custom item
  name: string;
  quantity: number;
  weight: number | null;
  equipped: boolean;
  attuned: boolean;
  notes: string;
}
```

The roll log lives in memory for the session and is not saved.

## 6. Modifiers, timed effects and homebrew

One small modifier type covers class features, feats, items, DM overrides and your homebrew, so the sheet has one place that applies them.

```ts
interface Modifier {
  target: string;      // "ac", "speed.walk", "hp.max", "ability.str", "save.dex",
                       // "skill.stealth", "initiative", "spellSaveDC", "attack.melee",
                       // "damage.melee", "resource.<featureId>.max", "resistance",
                       // "vulnerability", "immunity", "sense.darkvision"
  op: "add" | "set" | "cap" | "atLeast";   // cap = can't go above, atLeast = can't go below
  value: number | string;                  // a damage type for resistance etc.
  when?: string;                           // a toggle name, e.g. "raging"; off means ignored
}

type Duration =
  | { type: "permanent" }
  | { type: "untilRest"; rest: "short" | "long" }
  | { type: "rounds"; remaining: number }
  | { type: "untilTime"; at: number };     // in-game minutes since the campaign clock started

// Small fixed list. New trigger types get added when a real case needs one.
type Trigger =
  | { on: "heal"; action: "damageInstead"; ignoreResistance: boolean };

interface CustomEffect {
  id: string;
  name: string;
  kind: "feature" | "condition" | "curse" | "boon";
  description: string;
  active: boolean;
  uses?: { max: number; used: number; resetOn: "short" | "long" | "none" };
  modifiers: Modifier[];
  triggers: Trigger[];
  duration: Duration;
}
```

Your examples map like this:

- Vampire curse capping rage: `{ target: "resource.feature.barbarian.rage.phb24.max", op: "cap", value: 2 }` (the number is whatever you set).
- Temp HP that expires: `state.tempHp` with `tempHpExpires` set; the sheet clears it when the duration ends.
- Healing that deals unresistable damage: a curse with the `heal` trigger. The Heal button then subtracts the amount from HP and skips resistances, and the roll log says why.

## 7. Import pipeline

Run per book: `python import_books.py --book phb24 --only classes:barbarian,cleric,wizard`.

1. **Survey.** For every page: get the text layer with PyMuPDF and score it (share of words found in a word list, share of odd character runs, character count). Below the threshold, or no text: render at 300 DPI and run Tesseract. Save the chosen text, the score and the method to `ocr-cache\<book>\page-NNNN.json`. A cached page is never redone unless you pass `--redo-ocr`. The first run writes a page quality summary for the whole book, so we measure every page rather than relying on samples.
2. **Clean.** Apply OCR fixes (`ld8` to `1d8`, `l`/`I`/`1` inside dice and numbers, words split by stray spaces such as "pow er"). Each fix is logged with page, before and after.
3. **Locate.** `books.json` holds page ranges per section (Barbarian chapter, spell list, feats). I fill these in from the survey output (chapter headings it finds), not from memory, and you can check them against the PDF.
4. **Parse** each kind into the schema above.
5. **Validate** structurally:
   - every class progression has 20 rows, levels 1 to 20 in order;
   - proficiency bonus follows the standard progression (+2 at level 1, +1 every 4 levels);
   - spell slot rows agree between classes of the same caster type (Cleric and Wizard should match each other, half casters likewise), and slot counts never go down as level rises;
   - spells have level, school, casting time, range, components and duration;
   - feature levels named in the class text appear in the table's features column.
6. **Write** `data-pack\<book>\*.json` and `reports\import-report-<book>.html`. The report lists flagged entries first, then the rest, each with parsed data, PDF page, OCR used, and flags.

## 8. Testing approach

- **Python:** pytest for scoring, OCR fixes and parsers, using short made-up snippets so no book text ends up in git.
- **TypeScript:** Vitest. `tests\unit` checks rules logic with small invented fixtures (for example, a fake class whose table I write by hand to test the lookup code). `tests\book-data` checks derived values (proficiency bonus, slots, save DC, HP) against the real data pack. Because the data pack is git-ignored, those tests skip themselves when it is missing and run on your PC.
- **Milestone 1:** the level 6 Barbarian is entered by hand. I won't type rage counts or other book numbers in from memory, so the M1 file holds the values you enter (abilities, max HP, features as custom effects with use counters). Once the data pack exists, the same file links to the imported class and the values become calculated.

## 9. Choices I've made (tell me if you disagree)

- **electron-vite** for the build setup: one config for main, preload and renderer, and it pairs well with electron-builder.
- **Plain React state** (useState/useReducer) and plain CSS. No Redux, no CSS framework.
- **pytesseract** to call Tesseract, because the call is visible in your code; PyMuPDF has its own OCR wrapper but it hides what is happening.
- **wordfreq** for the "is this a real word" score, because it works offline and needs no word list file in the repo.
- **Portraits embedded** in the character file (resized small), so a character copied through Google Drive keeps its picture.
- **Content folder as a setting**, like the save folder. Point it at the shared Drive and your corrections reach your players.
- **Import Books button** only shows when the app can find Python and the project folder (your PC). Players never see it.
- **Core sheet lists** (the six abilities and the skills with their abilities) live in `app/src/shared/coreRules.json`, not in code. The Milestone 2 import checks them against the PHB.

## 10. Decisions after review

- **Multiclassing is in scope.** Levels are stored per class (`LevelRecord.classId`), hit dice are pooled per die size, and the level-up wizard (Milestone 3) offers any class at each level, checking multiclass prerequisites and proficiencies from the imported PHB data. Spell slots for multiclass casters come from the PHB multiclass table, imported and validated like the class tables.
- **Timed effects use an in-game clock set by the DM.** Game time is a count of minutes since the campaign started, shown as "Day 12, 21:30". The DM's app writes it to `campaign.json` in the shared save folder, and players' apps read it from there. When the clock passes an effect's `untilTime`, the effect ends (temp HP is cleared, modifiers stop applying). Rest and round durations still work as well. Built in Milestone 4, with the shared file in Milestone 5.
- **Books in scope:** PHB 2024, Xanathar's, Tasha's and Giants only. The DMG, Monster Manual and Curse of Strahd files are out of scope and the import refuses any book not listed in `books.json`.
- **Players never need the PDFs.** Everything the sheet and level-up wizard use is extracted into the data pack, which the build bundles. Page numbers stay on each entry for the DM to check against the book.
- **Milestone 2 onwards runs in Claude Code on the DM's PC**, so the import can read the PDFs directly. Milestone 1 is built in the cloud session.

## 11. 2024 rules only (decided during Milestone 2)

Every character uses the 2024 rules. 2014 books stay allowed as legacy content. Each change below was read from the 2024 PHB (page numbers are PDF pages), not from memory.

| Change | PHB source | Where it lives |
|---|---|---|
| A Hit Point Die heals roll + Con modifier, minimum 1 Hit Point | Rules Glossary, Short Rest (p.372) | `rules/rest.ts`, test in `rest.test.ts` |
| Long Rest: all HP, all spent Hit Point Dice, Exhaustion -1; Temporary HP last until used up or a Long Rest | Glossary, Long Rest (p.369); Temporary Hit Points (p.28) | `rules/rest.ts` |
| Exhaustion: D20 Tests -2 per level, Speed -5 ft per level, death at level 6 | Glossary, Exhaustion [Condition] (p.365) | `rules/exhaustion.ts`, roll log and Speed on the sheet |
| Inspiration is now Heroic Inspiration (reroll any die) | Glossary (p.367) | sheet label |
| Older backgrounds: +2/+1 or +1/+1/+1 to any scores, and an Origin feat of your choice; older species' ability increases are ignored | Chapter 2 sidebar (p.37) | `data-pack/phb24/legacy-rules.json`, character `origin` field |
| Same-named 2014 feats are replaced by the 2024 version (Slasher, Crusher, Piercer, Poisoner, Chef, Skill Expert, Fey Touched, Shadow Touched, Telekinetic, Telepathic) | Introduction, "What's New" (p.4) | `supersededBy` on Tasha's feats |
| An older Cleric subclass's Divine Strike or Potent Spellcasting is used only if chosen for Blessed Strikes | Cleric, level 7 (p.70) | `legacy-rules.json` |
| 2014 subclass chosen at level 3; earlier features arrive at level 3 | Your table rule (confirmed 2026-11-07) | `printedLevel` and `level` on each subclass feature |

The character file now has `ruleset: "2024"` and `origin: { backgroundIncreases, originFeat }`. `tools/book_import/sheet_to_2024.py` lists what changes for the three sample characters (written to `reports/`, never committed).
